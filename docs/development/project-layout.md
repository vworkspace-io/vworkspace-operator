# Project layout

**Status:** Alpha — planned layout, not fully implemented.
**Last Updated:** 2026-05-28

This is the intended directory layout for the operator's Go source tree, generated from the Kubebuilder scaffold. As of `2026-05-28` the repository contains the documentation tree, the `config/` and `hack/` directories, and a `README`; the Go code under `api/`, `controllers/`, and `internal/` is being added incrementally. Where this document describes a directory, it is the layout the project is converging on.

The Kubebuilder layout is deliberately conventional: anyone who has worked on a controller-runtime operator will recognize the shape. The vWorkspace-specific additions are confined to `internal/agent/`, `internal/engines/`, and `internal/helmengine/`, which are described below.

## What each directory holds

### `api/v1alpha1/`

The Go types for the CRDs the operator owns: `ApplicationInstance`, `Operation`, `Cluster`. The files use Kubebuilder markers (`+kubebuilder:object:root=true`, `+kubebuilder:resource:scope=Namespaced`, `+kubebuilder:subresource:status`, `+kubebuilder:validation:Pattern=...`) to drive `controller-gen`. Conditions and shared status types live in `conditions.go`; the `zz_generated.deepcopy.go` file is regenerated by `make generate`.

Add a new field on a CRD: edit `*_types.go`, run `make generate manifests`, commit both the Go change and the regenerated artifacts.

### `controllers/`

One file per top-level reconciler (`ApplicationInstanceReconciler`, `OperationReconciler`, `ClusterReconciler`). Each reconciler is a thin layer that:

1. Loads the CR.
2. Validates preconditions (delegating most validation to the admission webhook).
3. Materializes child resources (delegating engine-specific work to `internal/engines/`).
4. Reads child status (delegating mapping to `internal/conditions/`).
5. Writes back to the CR's status.

The reconcilers do not embed engine-specific logic. The Velero-specific code lives under `internal/engines/velero/`; the reconciler calls into it.

`suite_test.go` configures envtest for the package; individual reconciler tests live next to their reconciler.

### `internal/agent/`

The Pull-mode client and the outbound status batcher. The shape:

- `Poller` runs a goroutine that long-polls `/api/agent/jobs?cluster=X&wait=30s`, applies each job's payload (server-side apply if the payload is a manifest; otherwise it translates the intent into a CR), and posts ack/status/result.
- `StatusBatcher` queues outbound events from the reconcilers (via a channel), coalesces them, and flushes to `/api/agent/events` on a timer or when a size threshold is hit.
- `Credentials` manages the bootstrap credential's lifecycle: load on startup, rotate ahead of expiry, persist back to `Secret/vworkspace-system/vworkspace-operator-credentials`, redact in logs.
- `transport_longpoll.go` is the default transport. Other transports (gRPC, SSE) plug in behind the same interface and live next to it.

### `internal/engines/`

One package per (type, engine) combination, behind an `Engine` interface:

```go
type Engine interface {
    Materialize(ctx context.Context, op *opsv1alpha1.Operation, target *appsv1alpha1.ApplicationInstance) error
    Status(ctx context.Context, op *opsv1alpha1.Operation) (Status, error)
    Cancel(ctx context.Context, op *opsv1alpha1.Operation) error
}
```

`internal/engines/velero/` translates an `Operation` into a `velero.io/Backup` or `velero.io/Restore`; `internal/engines/workflow/` into a `workflows.argoproj.io/v1alpha1` Workflow; and so on. Adding a new engine is adding a sub-package and wiring it into the operation reconciler's engine registry.

### `internal/helmengine/`

The Helm engine adapter. Two sub-packages today:

- `flux/` — Materializes a `helm.toolkit.fluxcd.io/v2/HelmRelease` and the `HelmRepository` / `OCIRepository` that backs it. This is the default.
- `argocd/` — Will materialize an `argoproj.io/v1alpha1/Application`. The skeleton is present but the implementation is pending the Argo adapter milestone (see the parent project's ROADMAP).

The interface they both satisfy is small ("create or update the engine's CR; report its status"); the choice of engine is the cluster's `HelmEngine` setting, defaulted to `flux`.

### `internal/admission/`

Validating and mutating webhooks. Validating: the placeholder rule set for inline secret material; the capability check for `Operation` requests; the namespace allow-list for managed namespaces; the forbidden-version policy. Mutating: default values, ownership labels, security-context defaults on Job-engine Pods.

The webhooks are served by the operator pod on the standard kubebuilder port (`:9443`) and are registered by `config/webhook/`. TLS material is provisioned by cert-manager via `config/certmanager/`.

### `internal/conditions/`, `internal/labels/`, `internal/metrics/`

Cross-cutting utilities. The conditions helper centralizes "set this condition, preserve `lastTransitionTime` if the status did not actually change"; the labels package defines the canonical strings (`app.vworkspace.io/managed-by`, `app.vworkspace.io/cluster-id`, `ops.vworkspace.io/operation`, capability-annotation keys) so they are not duplicated; the metrics package registers the operator-specific Prometheus collectors documented in [../operate/observability.md](../operate/observability.md).

### `config/`

Kustomize bases for the chart. `config/crd/` and `config/rbac/` are generated; `config/manager/` and `config/webhook/` are hand-edited; `config/samples/` is documentation-grade fixtures used by the e2e tests; `config/workflows/` ships the operator's bundled `WorkflowTemplate` resources.

### `hack/`

Tooling that does not belong in `Makefile` itself. `hack/boilerplate.go.txt` is the file header the code generator adds; `hack/tools/` pins tool versions; `hack/verify-*.sh` are the CI scripts that gate PRs (`verify-generated.sh`, `verify-shellcheck.sh`, etc.).

### `test/e2e/`

Tests that spin up a real kind cluster, deploy the operator, apply CR fixtures, and assert on real behavior. Slow, but they catch bugs that envtest cannot (webhook TLS plumbing, real Helm releases, real Velero CSI snapshots).

### `cmd/manager/`

The main package. The operator binary is a Cobra command with two subcommands today:

- `run` — the manager (controllers + webhooks + metrics).
- `register` — the CLI helper that exchanges a one-time registration token. Same code path the `Cluster` reconciler uses internally.

The split keeps the binary single (one image, one binary, multiple subcommands) and is the standard Kubebuilder pattern.

## Where the Argo CD adapter will live

`internal/helmengine/argocd/` is the planned location. The expected scope:

- One `helmengine.Engine` implementation that materializes an Argo `Application` resource per `ApplicationInstance`.
- A status mapping from Argo's sync/health conditions to `ApplicationInstance.status.conditions`.
- An optional Git-source variant that points Argo at a Git repo Odoo writes to (an interaction with GitOps mode).

The adapter is intentionally late on the roadmap. The default `flux/` adapter is the path the project actively supports; the Argo adapter is the path for organizations that have standardized on Argo CD culturally. See [../adr/0002-helm-first-via-flux-helmrelease.md](../adr/0002-helm-first-via-flux-helmrelease.md) for the reasoning.

## What is missing from the layout today

As of `2026-05-28`:

- The Go source under `api/` and `controllers/` exists in skeleton form; many files are stubs.
- `internal/agent/` is being implemented; the long-poll transport is the only one present.
- `internal/engines/velero/`, `internal/engines/job/`, and `internal/engines/helmhookjob/` are the first three engines being wired up.
- `internal/helmengine/argocd/` is a stub.
- `test/e2e/` exists but is sparse.

The documentation chapter you are reading is intentionally written against the eventual layout, not the current one. As files arrive, the planned-vs-actual gap will shrink; the layout above is the contract the engineering work targets.
